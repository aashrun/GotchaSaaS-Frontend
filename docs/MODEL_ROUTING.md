# Gotcha SaaS model routing

The enforced policy is `gotcha-saas-routing-v3`. When `NODE_ENV=development` (or unset), every coding and research role is locked to OpenRouter `openai/gpt-6-luna`. Active paid subscriptions, 3D tasks and manual premium-model selections cannot override this. The model picker exposes only Luna, estimates use its prices and economy limits, and provider dispatch checks the policy again. Agent and legacy queued jobs are checked before sandbox startup; old premium snapshots cannot run in development and need a new Luna request. If enabled Luna or OpenRouter configuration is missing, generation stops without selecting another model. Voice transcription keeps its separate speech model.

Outside development, ordinary web frontend work uses GPT: Luna on economy, Sol on balanced/pro. Backend work uses Luna on economy, Sonnet on balanced, and Sonnet for ordinary pro work with Opus for architecture. Explicitly selected GPT/Claude coding models can override backend roles; selecting Claude does not redirect ordinary web frontend work to Claude. Three.js/WebGL/3D requests may use the plan-approved Claude frontend specialist. Dependency/runtime support must still be checked: routing does not add unsupported packages. No automatic fallback to an arbitrary enabled model is allowed. Missing GPT configuration blocks generation.

Every queued job records role models, prices, policy version, routing reason and allowed budget. Context/output/compute limits, the funded credit check, permissions and supported tools remain server-owned. A model cannot raise the user's plan, add funds or approve external actions. Claude Code and Codex are agent products; the current runtime calls the configured underlying GPT/Claude models through OpenRouter, not those products' desktop harnesses.

## How selection and costs work today

Selection is a deterministic server policy, not a Jev call or an automatic benchmark download. It classifies the prompt and existing source into frontend, backend or architecture, loads the authenticated user's server-side active subscription, and snapshots the permitted specialist for each role. The agent can switch only among those snapshotted roles through a validated tool. Ordinary frontend requests stay with GPT. The same choices are enforced at estimate, queue and execution boundaries.

The maximum reservation is the largest configured per-call input/output cost across the allowed roles, multiplied by the call cap, plus a $0.01 bounded-search allowance and the allowed compute seconds multiplied by the configured compute rate. Context bytes are conservatively used as the input-token ceiling; reference token allowance is added. Development currently caps output at 4,000 tokens, uses ten calls/210 seconds for tic-tac-toe and twelve calls/240–300 seconds for other economy jobs. Prices are configured model-catalog data, snapshotted for that job.

At settlement, OpenRouter-reported cost is preferred; otherwise actual token counts and snapshotted rates supply an estimate. Estimated elapsed E2B compute is added, converted at `CREDITS_PER_USD` and rounded up. The current 1,000 credits per dollar is a ledger conversion, not a retail subscription price or a profit margin. Unused reservations return to the account. Failed platform builds waive the customer's charge, while their incurred provider cost still counts against the server's funding limit. This is usage accounting, not reconciliation against an imported E2B invoice. See [the broader economics and preview lease](HARNESS_STRATEGY.md).

## Jev recommendation

Jev can return typed choices, rubric scores and probabilities. It can help classify intent, estimate task difficulty, choose between permitted tools, assess whether clarification is useful, and advise whether a failed attempt needs escalation. The vendor recommends small independent questions rather than one broad question weighing many unrelated factors: [TypeSafe documentation](https://docs.typesafe.ai/introduction).

Do not enable it as the final authority for model selection yet. One independent preprint found neither tested decision model exceeded chance for zero-shot model routing on its evaluation. That is evidence to measure our own tasks, not proof Jev can never help: [paired evaluation](https://arxiv.org/abs/2610.02267).

A safe next evaluation is shadow routing: give Jev a redacted requirements summary and a small allowed label set such as ordinary frontend, backend CRUD, security architecture, 3D. Include supported stack, current plan/cost ceiling, known model availability and dated measured performance. Record its advice without changing live routes, with a short timeout and deterministic fallback. It receives no credentials and never decides access permissions, spending authority or publication approval.

Model profiles need our own held-out application builds: end-to-end requirement pass rate, first-attempt success, repair count, total provider plus compute cost, latency, tool reliability and security-case results. Public benchmarks are dated supplementary evidence; a generic ranking cannot establish UI quality or our backend success rate. Select the cheapest allowed model meeting the task's measured quality floor. Consider stronger models for authentication/billing/migrations only within the reviewed plan budget. Uncertain advice falls back to the explicit policy. Separate cost from confidence: a high confidence number is not a verified success probability until calibrated against these cases.

The four-app Luna run is a small diagnostic sample, not enough to establish superiority between Luna, Sol, Sonnet or Opus. Jev is not connected to live routing in this change; no new router provider calls or untested cost-saving claims are made.
