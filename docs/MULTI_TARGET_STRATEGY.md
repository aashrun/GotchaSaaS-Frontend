# Multi-target application strategy

## Product scope and implementation

The supported product targets are Web, PWA, Mobile and Desktop. Websites, dashboards, customer portals, mobile-friendly sites and browser games use Web. PWA adds installation and an offline application shell. Mobile uses real Expo / React Native source. Desktop uses a protected Electron shell around the generated React renderer. Bots and extensions are outside this release.

The creation composer keeps a single optional “Application type” selector under Options. Auto distinguishes a responsive website from a native Android/iPhone request. Ambiguous “mobile app” requests ask browser versus installable web versus native. Nontechnical users are not required to select languages, frameworks or source directories.

The backend owns a versioned build plan in project settings. The plan records target, platforms, frontend, backend, styling, stable application identity, source structure and setup answers. Initial setup is question-driven when the user explicitly chooses a language without a framework. Requests for JavaScript or TypeScript frontend, JavaScript backend, Python, Java and Ruby receive appropriate framework questions. Each modal has concrete choices and a free-text field. Generic Go/Rust/PHP and unsupported framework preferences are retained and blocked rather than replaced with a supported stack. Explicit React/Angular/Vue and Python framework choices are honored. React JavaScript projects export JavaScript rather than silently retaining TypeScript source.

Defaults are React/TypeScript plus Tailwind/shadcn for web renderers, Expo/React Native with StyleSheet for mobile, and Electron with React for desktop. Backend-free projects stay backend-free. Supported server images provide Node/Express and Python FastAPI, Flask or Django. Java/Spring, Ruby/Rails, Angular, Vue, Tauri, Flutter, Kotlin/Swift and other custom frameworks require their own registered, tested adapters; they are not marketed as working runtimes. Native apps with Python backends need a combined runtime or a separate API project; they are explicitly gated. Server-backed desktop requests are also gated until a reviewed HTTPS API/session adapter is implemented; current packaged desktop apps use local browser storage.

Foundation questions precede credit estimates and model calls. Named empty projects capture the first actual prompt under the same pristine-source lock before choosing a stack. Answers are tenant checked, recorded and used to regenerate only pristine revision-zero templates. The foundation is locked after development starts; framework migration requires a separate project/adapter workflow. During feature development, the existing agent question tool supports blocking checkpoints and independent work with deferred paths. The model receives the approved plan, available runtime, prior answers and file inventory; it cannot select an unregistered image, change package dependencies or execute arbitrary platform commands.

## Preview, runtime and delivery

| Target  | Source / execution                                                            | Right-side preview                                                                   | Delivery                                                                          |
| ------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- |
| Web     | Vite/React, optional Node/Python API and private PostgreSQL                   | Browser UI and explicit backend lease                                                | Existing reviewed web deployment or source ZIP                                    |
| PWA     | Web source plus protected manifest and service worker                         | Browser UI; separate signed install/offline preview                                  | HTTPS site with HTML, manifest and worker                                         |
| Mobile  | Expo, React Native, JS/TS, optional Node API; SecureStore for native sessions | Phone-shaped React Native web rendering, labeled distinctly from native-device tests | Owner's Expo/EAS build configuration and Android/iOS guides                       |
| Desktop | React renderer, Electron sandbox/preload, unique app identity                 | Renderer preview with native-package limits shown                                    | OS build matrix; manual unsigned packages, then signing/notarization and OS tests |

Mobile source includes unique Android/iOS identifiers and EAS preview/production profiles. Application secrets stay in the separately hosted backend; only its public HTTPS URL is an Expo public setting. Native authentication uses bearer sessions stored with SecureStore, omits browser credentials, and preserves origin checks for browser callers. Preview account/data interactions use the existing authenticated runtime broker. All production APIs still need application-specific hardening, durable infrastructure and deployment verification.

The Electron main process and preload are protected. Node integration is off, context isolation and renderer sandboxing are on, popups and navigation are restricted, and the default renderer cannot make external connections. The CI workflow uses an explicit manual trigger and three OS runners. No workflow, store submission or public publishing is silently started. Native OS capabilities and network integrations need reviewed, scoped adapters rather than unrestricted IPC.

Every PWA project gets a distinct preview hostname. Signed tickets bind user, project, revision, expiry and nonce. Current tenant membership and suspension are checked; preview cookies never authenticate the Gotcha control plane. Service workers run on the generated project's origin, not the application origin. The worker caches only the shell/manifest and never API, authentication or platform responses. Offline access is an application-shell capability, not automatic offline synchronization of database records. Production needs a separate root domain, wildcard DNS/TLS and a preview proxy. Development uses project-id.localhost:7015.

All supported source executes only inside dependency-preinstalled E2B images with public traffic denied. Runtime selection is server-owned and snapshotted with the job. Builds, backend contracts, browser interactions and native packaging are reported as separate stages. Browser success never marks a native package or device verified. Cloudflare publication explicitly handles PWA files and refuses native targets.

## Verification performed on 2026-10-14

- Real offline images: Expo browser build and interactions, with/without Node backend; FastAPI/Flask/Django signup/login/records and user-isolation contracts; desktop renderer build/preview. All passed after correcting Python login validation to preserve the existing authentication contract.
- Real Gotcha agent generation through OpenRouter: mobile, PWA and desktop water trackers. Every coding call used GPT-6 Luna. All three completed with add/reset browser evidence. The combined model spend was $0.007430841; estimated job compute was $0.008946908. Other sandbox contract checks and image preparation are separate operator costs.
- The generated PWA passed manifest/raster-icon checks, real service-worker control, offline reload and offline interaction. Cache inspection showed only the shell and manifest.
- The generated desktop app was packaged as an unsigned macOS .app and played in its actual native window. Add/reset and Electron isolation preferences passed. Windows/Linux packages and native Android/iOS binaries/device features were not verified.
- Automated regression: 86 backend tests passed, nine optional provider contracts skipped; 20 browser workflows passed. Foundation tests cover tenant scope, no credit deductions, immutable/idempotent answers, source regeneration and native-project duplication.
- Owner chose to connect Expo later. Android/iOS package builds remain gated. App-store release, signed Windows/Linux distribution, macOS notarization and public deployment require owner configuration/approval.

## Growth and operating model

Extend the registry one stack at a time: protected scaffold, dependency lock, offline image, fixed commands, acceptance contracts, artifact format and preview adapter. Register a runtime only after positive and negative contract checks pass. Keep language selection separate from model routing: development remains Luna; production coding roles follow subscription budgets. Preserve immutable approved source/revision for packaging requests, record provider receipts and measured usage, and use idempotent queue jobs with per-tenant concurrency/cost ceilings for future EAS/OS builders. Signing credentials must be encrypted, tenant scoped, short lived where supported, and absent from generated source and logs.

Use feature folders inside src and separate server modules as complexity grows. Avoid premature microservices or asking nontechnical founders to pick infrastructure. Larger generated apps need a broader evaluation suite, dependency registry, architecture review and durable deployment/runtime support before production-readiness claims.

## Dependency release gate

The platform production dependency audit reports zero vulnerabilities. The separate Expo image audit identifies upstream build-tool vulnerabilities; it is not a clean security audit. UUID is overridden to patched 11.1.1. [braces stack exhaustion](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) and [node-forge signature verification](https://github.com/advisories/GHSA-86w9-cpqp-85rv) still list no patched release on 2026-10-14. The default image has no internet/public ingress and accepts only protected build configuration with bounded execution, limiting exposure during preview generation. Those isolation controls do not fix the dependencies or certify Expo signing/package delivery. Resolve/replace affected tooling and re-audit before native distribution. Do not downgrade Expo to the unrelated old major suggested by an automated audit fix.
